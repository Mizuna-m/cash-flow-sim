# 実装方針メモ（MVP着手用）

## 1. このプロダクトの本質

このシステムの本体は、家計簿UIではなく「実績・予定・予測を統合して、将来の資金ショートを検知できる日次シミュレーション基盤」である。

特に重要なのは以下の3点。

* 理論残高と現実残高を分けて扱うこと
* 支出発生とカード決済を分離して扱うこと
* 日常支出予測とイベント支出を同じ時系列に重ねること

そのため、実装はUI起点ではなく、計算ロジックとデータ境界を先に固める方針とする。

## 3. MVPの実装優先順位

MVPでは、受け入れ条件と業務ルールから逆算して、以下を優先する。

### 最優先

* 日次シミュレーション
* 理論残高 / 現実残高の算出
* カード利用残高の蓄積
* カード引落予測の生成
* ショート判定

### 次点

* Transaction / ScheduledEvent / CardPayment / BalanceEvent の CRUD
* Project / Category / Group 集計
* シナリオ ON/OFF
* 残高推移グラフ

### 後回しにするもの

* 銀行・カード自動連携
* OCR
* 高度な予測アルゴリズム
* 複雑な認証
* 多通貨の高度な換算UI
* 投資評価の高度化

## 4. 実装時の重要な解釈

実装時にブレやすい点は、以下の解釈で固定する。

### 4.1 支出入力

* `Transaction.amount` は正負で表現する
* 支出は負、収入は正
* 支払手段は必須入力にしない
* `card_id` は任意とし、未指定時は `default_card` に割り当てる
* `Transaction` の主情報は `description / payee / payee_detail / note / category_path` に分け、`tags` は `project` や `custom` など補助検索用に絞る
* 大量入力を前提に、`payee` を軸にした `payee_detail / category_path / account / card / project` のサジェストと既定候補補完を入れる
* サジェスト UI はキーボードだけで完結操作できることを前提にする

### 4.2 残高モデル

* 理論残高は「発生ベース」
* 現実残高は「口座残高ベース」
* ショート判定は現実残高で行う
* 残高の確認粒度は日次を基本とし、既存スプレッドシートの行単位 running balance をそのまま再現することは MVP の必須条件にしない

### 4.3 カード処理

* 支出時は理論残高を減らし、カード残高を増やす
* 引落時は現実残高を減らし、カード残高を減らす
* 予測より実績を優先する

### 4.4 Forecast

* 初期はオンデマンド計算
* 保存は最小限
* 予測ロジックは差し替え可能なモジュールに分離する

### 4.5 MVP境界

* 多通貨はデータモデルで受け止めるが、最初の完了条件からは外してよい
* 投資はモデル上の拡張余地を確保しつつ、MVP初期実装では主要シミュレーションから切り離してよい

## 5. 推奨アーキテクチャ

技術方針に合わせ、Next.js モノリス構成を前提にする。

```text
Next.js App Router
├─ UI
├─ Route Handlers
├─ Application Services
├─ Domain
│  ├─ simulation
│  ├─ forecast
│  ├─ card-payment
│  └─ aggregation
└─ Infrastructure
   ├─ db
   └─ repositories
```

### レイヤ責務

* UI: 入力、可視化、シナリオ比較
* Route Handlers: リクエスト境界、DTO変換
* Application Services: ユースケース単位の調停
* Domain: 純関数ベースの計算とルール
* Infrastructure: PostgreSQL 入出力、キャッシュ、マイグレーション

### 守るべきルール

* シミュレーションは純関数で実装する
* DB に複雑ロジックを書かない
* 派生結果は原則保存しない
* 差し替え可能性が必要なロジックは `domain/` に閉じ込める

## 6. 実装フェーズ

### Phase 0: 着手前固定化

目的:

* 文書から実装対象を固定する
* 以後のセッションで迷わない状態を作る

成果物:

* 本ドキュメント
* `task-list.md`

### Phase 1: プロジェクト基盤作成

目的:

* 実装できる土台を作る

作業:

* Next.js + TypeScript + Tailwind の初期化
* Podman / db / app のコンテナ構成
* Lint / Format / Test 基盤の導入
* 環境変数方針の確定

完了条件:

* アプリと PostgreSQL がローカル起動する
* 空のヘルスチェックAPIが動作する

### Phase 2: DBスキーマと基礎CRUD

目的:

* MVP中核データを永続化できるようにする

対象:

* Account
* CreditCard
* Transaction
* ScheduledEvent
* BalanceEvent
* CardPayment

完了条件:

* 基本CRUDが API 経由で操作できる
* 日付、金額、`order_index`、`payee`、`payee_detail`、`description`、`note`、`category_path`、補助タグ JSON が保存できる

### Phase 3: シミュレーションコア

目的:

* 受け入れ条件の中心である日次残高計算を成立させる

作業:

* イベント正規化
* 日次イベント収集
* 同日内順序ソート
* 理論残高 / 現実残高 / カード残高更新
* ショート判定

完了条件:

* seed データで AC-01, AC-02, AC-03, AC-04, AC-16, AC-21 を通せる

### Phase 4: 予測ロジック

目的:

* 将来予測をシミュレーションへ接続する

作業:

* DailySpendForecast の初期ロジック実装
* CardPaymentForecast 生成ロジック実装
* 実績入力時の予測無効化ルール実装

初期アルゴリズム案:

* 日常支出予測は直近N週間または直近Nか月のカテゴリ別平均を元にする
* MVPでは説明可能性を優先し、複雑な機械学習は行わない

完了条件:

* AC-05, AC-06, AC-08, AC-09, AC-17 を満たす

### Phase 5: 可視化と最小UI

目的:

* 最低限の意思決定支援画面を成立させる

優先画面:

* ダッシュボード
* 取引登録画面
* 予定登録画面
* シミュレーション結果画面
* Project / Category / Group 集計画面

完了条件:

* ユースケース UC-01, UC-02, UC-03, UC-05, UC-06 を一通り操作できる

### Phase 6: シナリオと移行導線

目的:

* 実運用に必要な比較と移行を整える

作業:

* ScheduledEvent の ON/OFF
* シナリオ比較
* CSV / ODS インポート前提の初回データ投入導線
* 列マッピング確認と dry-run
* 既存スプレッドシートからの最小移行

完了条件:

* AC-18, AC-19 を満たす
* 直近3〜6か月のデータ投入で確認できる

## 7. 仮実装してはいけない箇所

以下は見た目だけ先に作ると、あとで大きく壊れる。

* 理論残高と現実残高を同一値として扱う実装
* 支出とカード引落を同一イベントとして扱う実装
* 予測より実績を優先するルールを省略する実装
* `order_index` を無視する実装
* DB クエリに計算ロジックを埋め込む実装

---

## 8. 後で差し替え可能にすべき箇所

* 日常支出予測アルゴリズム
* カード自動割当ルール
* 派生結果キャッシュ方式
* シナリオ比較の差分計算方法
* 多通貨換算ロジック

これらは interface を挟み、UI や DB スキーマに強く結合させない。

---

## 9. まず seed data で成立確認すべきユースケース

最初のテストデータは、以下を必ず含める。

1. 給与振込
2. 家賃などの定期支出
3. 日常支出の複数日入力
4. カード支出とその翌月引落
5. Project付きイベント支出
6. 資金移動
7. 実績がある日は予測を適用しないケース
8. 将来ショートするケース
9. 同日内順序で結果が変わるケース

## 10. 現時点の未決事項

実装中に最初に詰まりやすいのは以下。

* `Scenario` を独立エンティティにするか、イベントの有効状態だけで MVP を回すか
* `DailySpendForecast` を保存するか、毎回生成するか
* Account ごとの現実残高集計と「全体現実残高」の表現をどう両立するか
* 投資口座を MVP の現実残高に含めるか
* 多通貨を最初の seed/test で扱うか

現実的には、まずは以下の仮定で着手してよい。

* シナリオは `Scenario` + `ScenarioEventToggle` で後から拡張できるようにしつつ、初期はイベント有効フラグ中心で実装
* `DailySpendForecast` はオンデマンド生成し、必要ならキャッシュ
* MVP初期は単一通貨前提の seed/test を先に作る

---

## 11. 最初の実行順

次のセッションでは、以下の順で着手するのが最短。

1. アプリ雛形とコンテナ基盤を作る
2. DB スキーマを作る
3. seed データを作る
4. シミュレーション純関数を実装する
5. テストで受け入れ条件を先に固定する
6. その後に API と UI を薄く載せる

この順なら、計算の正しさを中心に据えたまま前進できる。
