Codex に渡す前提なら、要件定義書だけだとまだ足りない。
特にこのテーマは **「見た目のCRUD」より「計算規則と概念の解釈」** が本体なので、そこを別紙で明文化しておくと取りこぼしが減る。

優先順でいうと、追加で必要なのはこのあたり。

---

## 1. 業務ルール一覧

一番重要。

要件定義は「何をしたいか」までは示せるが、Codex が実装で迷うのは「どう解釈するか」。

たとえば明文化すべきもの:

* 日次集計だが、同一日内の前後関係はどう表現するか
* 資金移動は収支とどう区別するか
* クレカ利用日と引落日をどう扱うか
* 借入・返済・リボ残高・割賦残高をどう表現するか
* 投資口座への移動は「支出」ではなく資産振替なのか
* Project 付き支出と日常支出の関係
* 予測値はどこまで自動生成し、どこから手動補正か
* 年跨ぎイベントの開始・終了条件
* 残高ショート判定の基準値

これは「仕様書」というより **業務ルールブック** として独立させたほうがいい。

この手のシステムは用語の解釈ズレで事故る。

最低限定義したい語:

* 実績
* 予定
* 予測
* 資金移動
* 支出
* 口座
* 資産
* 負債
* 実質資産
* Project
* ProjectType
* Category
* CategoryGroup
* 日常支出
* イベント支出
* 残高

* 引落予定額

特に **支出だが資金移動ではないもの / 資金移動だが費消ではないもの** を分けて定義するのが大事。

## 3. 画面や操作ではなく「ユースケース詳細」

ユーザーストーリーの次段。

例:

* 来月ショートしないか確認する
* 旅行イベントを追加して影響確認する
* 通常生活費を実績から予測反映する
* クレカ引落予定を含めて資金繰り確認する
* 投資口座へ避難している資金の取り崩し余地を見る

各ユースケースについて

* 入力
* 前提条件
* 処理の考え方
* 期待出力
* 例外
  まで書く。

Codex はここがあると画面構成や API 単位を切りやすい。

---

## 4. 計算仕様書

実装に最も直結する文書。

これはほぼ必須。

書くべき内容:

* 日次残高計算の基本式
* イベント適用順
* 同日内順序の扱い
* クレカ締め・支払の変換規則
* 定期支出生成ルール
* 日常支出予測の算出ルール
* シナリオ ON/OFF 時の反映方法
* 実質資産算出式
* 投資資産の評価基準切替ルール

ここが曖昧だと、Codex は見た目だけ作って中身を仮置きしがち。

---

## 5. データモデル草案

ER 図まで厳密でなくていいが、少なくとも以下は欲しい。

* エンティティ一覧
* 主キー候補
* 必須項目
* 関係
* 履歴保持の要否
* mutable なもの / immutable なもの

特にこのシステムは

* Transaction
* BalanceEvent
* ScheduledEvent
* Account
* Project
* Forecast
* Scenario
  の境界が曖昧になりやすいので、文章だけでなく表で持っておくと強い。

## 6. サンプルデータ集

かなり効く。

実データそのものではなく、典型ケースを数件ずつ作る。

例:

* 給与振込
* 家賃
* コンビニ支出
* クレカ利用
* クレカ引落
* 借入実行
* 借入返済
* 投資口座への積立
* 旅行 Project 紐付き支出
* 年跨ぎイベント
* 残業代のような変動収入

Codex はサンプルがあるとテストデータと seed を作りやすい。

---

## 7. 受け入れ観点一覧

実質的な MVP 完了条件。

ユーザーストーリーごとの受け入れ条件とは別に、
**システムとして最低限できていれば着手成功とみなすライン** をまとめる。

たとえば:

* 1年分の残高推移が表示できる
* クレカ引落を未来予定に変換できる
* 日常支出予測を反映できる
* Project 別集計ができる
* シナリオ比較ができる

これは Codex に「どこまで作れば第一段終了か」を伝える文書になる。

---

## 8. 非対象・後回し一覧

これも重要。

Codex は善意で広げがちなので、切る範囲を書く。

例:

* 銀行 API 自動連携はやらない
* OCR はやらない
* 多ユーザー対応はしない
* 家族口座の共有はしない
* 税務用途の厳密帳簿は対象外
* 会計仕訳機能は対象外

---

## 9. 既存スプレッドシートからの移行方針

今回かなり大事。

要件定義を読んでも、Codex は「今の運用をどう引き継ぐか」が見えない。

書くべきこと:

* どのブックを新システムへ取り込むか
* どれは当面スプシ継続か
* カラム対応表
* 欠損時の扱い
* Project ID など既存識別子の継承有無
* 初回データ投入の粒度

---

## 10. 意思決定メモ / ADR

小さくてもあると強い。

今回すでに出ている重要判断:

* 日次粒度を基本とする
* 同日内順序は保持する
* PostgreSQL を主軸とする
* セマンティクスは柔軟構造を許容する
* 日常支出は補助ではなく中核
* まずは個人最適
* 入力容易性より意思決定支援を優先

---

## 11. 開発運用ノート

実装が進むと、仕様書だけでは拾えない「開発時の暗黙知」が増える。

たとえば:

* `npm run build` の後に `podman compose restart` まで必要
* 依存追加時に container 側 `node_modules` の再同期が必要
* 仕様文書と OpenAPI の更新順をどう分けるか
* import / seed / compose まわりの再実行手順

これは仕様ではなく **開発運用の知見** なので、別紙の living document として管理したほうがよい。

こういう判断は会話に埋もれやすいので、別紙で固定するとブレない。

## 最低限これだけあればかなり強い

まず作るなら、この 5 点で十分実装に入れる。

1. 業務ルール一覧
2. 計算仕様書
3. データモデル草案
4. サンプルデータ集
5. 非対象・後回し一覧

## Codex向けに特に効く1枚

さらに実務上いちばん効くのは、**「実装着手メモ」** を1枚作ること。

内容はこれだけでいい。

* このプロダクトの本質は何か
* MVP の最優先機能は何か
* 仮実装してはいけない部分はどこか
* 後で差し替え可能にすべき箇所はどこか
* まず seed data で成立確認すべきユースケースは何か

これがあると、Codex が UI から作り始めて本質を外す事故が減る。

必要なら次で、そのまま保存できる形で
**「Codex引き渡し用 追加ドキュメント一式の章立てテンプレート」** を作る。
